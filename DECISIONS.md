# Принятые проектные решения (DECISIONS.md)

## Решение 1: Вынесение изменяемых параметров в именованные константы
**Проблема:** В индивидуальном варианте 7 ставка НДС составляет 40%, а также существуют жесткие границы для цены, количества и скидки. Если бизнес-требования изменятся (например, НДС станет 20%), поиск и замена "магических чисел" по всему коду приведёт к ошибкам.
**Решение:** Все пороговые значения и ставка НДС объявлены как `private static final` константы в начале класса `PurchaseCalculator` (например, `VAT_RATE = 40.0`).
**Обоснование:** Это реализует принцип DRY (Don't Repeat Yourself) и открытости/закрытости (OCP). Для изменения требования достаточно поменять значение в одной строке, не затрагивая логику вычислений.

## Решение 2: Разделение ответственности между методами (Decomposition)
**Проблема:** Размещение всей логики (ввод данных, валидация, математические расчёты, вывод в консоль) в одном методе `main` делает код монолитным, нечитаемым и сложным для тестирования.
**Решение:** Логика разделена на три группы приватных методов:
1. `validate(...)` — отвечает только за проверку бизнес-ограничений.
2. `calculateBaseSum`, `calculateDiscountAmount`, `calculateVat`, `calculateTotal` — отвечают только за чистые математические вычисления.
3. `getIntInput`, `getDoubleInput` — отвечают за безопасный ввод данных.
**Обоснование:** Метод `main` теперь выполняет только роль координатора (оркестратора). Это упрощает отладку: если ломается расчёт НДС, мы смотрим только в `calculateVat`, не отвлекаясь на код ввода данных.
